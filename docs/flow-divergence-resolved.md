# 最后一个未决问题：**流程与理线的分歧，结论是没有分歧**

## 1 问题是什么

| 项 | 状况 |
| --- | --- |
| `design-flow.json` 与 `cable-routing.json` | **已携带进 `data.ts`** ✓ |
| 游戏读它们吗 | **不读**（各 0 次引用）✓ 游戏自己实现了一套 |

**所以「设计写了一套、游戏另写了一套」** ✗ 问题一直是：这算不算缺口 ✗

## 2 逐条对照

**设计里的七个步骤**：

| 步骤 | 消耗 | 工时字段 |
| --- | --- | --- |
| 确定定位 | —— | —— |
| 选择配件 | —— | —— |
| 设计装配与外观 | owner, labor | designHours, developmentLaborHours |
| 制作样机 | bench, labor | assemblyHours, developmentBenchHours |
| 测试修改 | labor, test | testSetupHours, testStationHours, developmentTestHours |
| 命名定价 | —— | —— |
| 交付或投产 | labor | packingHours |

**游戏里的阶段**：

    设计打样 → 研发工位准备 → 研发验证 → 手工装配 → 外观工艺 → 测试准备 → 压力测试 → 包装交付 → 返工预留 → 返工测试预留

**逐项对应**：

| 设计 | 游戏 | 一致吗 |
| --- | --- | --- |
| 设计装配与外观 | 设计打样 | ✓ |
| 制作样机 | 研发工位准备 + 手工装配 | ✓ |
| 测试修改 | 研发验证 + 测试准备 + 压力测试 | ✓ |
| 交付或投产 | 包装交付 | ✓ |
| （外观工艺是设计描述过的额外工序） | 外观工艺 | ✓ |
| **测试修改里的返工** | **返工预留 + 返工测试预留** | ✓ |

**两类都没有矛盾** ✓ 游戏只是把设计的步骤拆得更细 ✓

## 3 返工本来就是设计里的一部分

`design-flow.json` 的 `test_revise` 步骤里**已经有**：

    costFields: ["reworkConsumables"]
    note: "测试台工时决定故障在工坊内被发现还是流出到客户"

**所以返工不是我在游戏里新加的机制** ✓ 它一直在设计里 ✓ 我做的只是**让它真的消耗工时** ✓ 因为设计的规则说：

> everyFieldClaimed：每个工时字段必须**恰好属于一个步骤**，不能有工作没被计入或重复计费

## 4 为什么游戏不读那两个文件

| 文件 | 性质 | 游戏为什么自己实现 |
| --- | --- | --- |
| `design-flow.json` | **规则的说明**（哪些工序消耗哪些资源） | 游戏要按自己的状态机执行 ✓ 读一份散文描述并不能驱动它 ✓ |
| `cable-routing.json` | 同上 | 同上 |

**这与其它十一个文件不同** ✗ ——`components.json`、`economy-candidate.json` 那些是**数据** ✓ 游戏必须读 ✓ 而这两个是**规则描述** ✓ 游戏实现它、不解析它 ✓

## 5 结论：**不是缺口**

| 判据 | 结果 |
| --- | --- |
| 设计与游戏在**实质**上一致吗 | **一致** ✓ 逐项对应，无矛盾 |
| 有校验守着它们一致吗 | **有** ✓ `check:flow` 验证每个工时字段恰好归属一个步骤，`check:design-to-game` 验证游戏实现了设计里声明的规则 |
| 需要游戏改成读文件吗 | **不需要** ✗ 规则描述文件的价值是**可读、可校验**，不是被程序解析 |

**所以这个悬了很久的问题可以关掉了** ✓

## 6 唯一值得改的一点

**游戏里那两个新阶段的名字**（返工预留 / 返工测试预留）在 `design-flow.json` 里没有对应词 ✗ 对读设计的人来说，会以为返工是新加的 ✓

**但因为设计里 `test_revise` 已经写了 `reworkConsumables`** ✓ 而且规则明确「七步固定」✓ 所以**加词反而会破坏那条规则** ✓

**结论：不改。** 这份文档就是那句说明 ✓
