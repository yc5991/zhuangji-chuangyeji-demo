# 客户硬性要求与迟到状态

本轮查出两个**核心玩法规则在仿真器里根本不存在**

## 1 硬性要求从未被检查

客户模型里每个原型都带一套硬性门槛：

| 门槛 | 例 |
| --- | --- |
| `minimumRamGB` | 学生机至少 8G |
| `minimumStorageGB` | 办公买家至少 120G |
| `requiredDiscreteGpu` | 玩家必须有独显 |
| `minimumVramGB` | 玩家至少 2G 显存；创作者至少 2G |
| `maximumNoiseBurden` | 家庭机噪声不超过 45 |
| `minimumScores` | 各用途分下限 |

`check:customers` 会验证**参考配方**满足这些门槛。但仿真器里的 `fitOf` **只用了软性的用途分比例**：

    用途分 ÷ 期望分，再按权重平均

**硬性门槛一个都没查。** 也就是说玩家造一台没有独显的机器，玩家客户照样会来买

**已修**：`fitOf` 现在先调用 `satisfies(recipe, requirements)`，不满足该原型的机器**该原型的权重直接归零**

## 2 是一个「迟到」状态完全没有实现

口碑模型定义了三种结果：

| 结果 | 口碑变化 |
| --- | ---: |
| 准时交付 | +0.04 |
| **迟到** | **−0.02** |
| 缺货 | −0.15 |

但仿真器只有两种：

    missedCommitment ? 缺货 : 准时

`lateMeetingRequirements` **从未被读取**。任何一个月只要没做满，就一律按「缺货」扣 0.15

**已修**：三种结果全部可达——一个月**交付了一部分**算迟到，**一台都没交**才算缺货

## 3 实测影响

**利润完全没有变化**（三条路线都是 0 差额）——因为参考配方本来就通过各自原型的硬性门槛。**这条规则只对玩家实际造出的不合格机器生效**，这正是它应有的效果

但**迟到状态改变了一个压力测试的结果**：

| 困难档 × 需求下降 35% × 精品 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 销量 | 2 | **9** |
| 利润 | −4129 | **+7686** |
| 破产 | **第 3 月破产** | 不破产 |

原因是修复前存在一个**死亡螺旋**：交 2 台也算「缺货」扣 0.15 → 口碑下降 → 需求下降 → 交得更少 → 再扣 0.15。**修复后交了一部分只算迟到（−0.02），螺旋被打断**

这是**修 bug 顺带修好的**：一个只交付了 2/9 的月份被当成完全没交付，本来就是错的

## 4 难度分离不受影响

| 难度 | 可承受亏损月数 |
| --- | ---: |
| 简单 | 7.95 |
| 普通 | 2.08 |
| 困难 | 1.23 |

三条路线规则（精品<量产、混合最大、混合<精品+量产）全部保持

## 5 校验强制项

`check:seams` 新增：

- 仿真器**必须真的调用** `satisfies`（否则报出「硬性门槛从未被检查，不合格的机器照样能卖」）
- **三种口碑结果都必须被实际应用**（定义了却不使用即失败）
- **迟到必须严格介于准时与缺货之间**，否则中间状态没有意义
