# 决策落地脚本

六项决策的改动散在多个文件里，手工一轮一轮改容易漏。`tools/apply-decisions.cjs` 把它们做成**一次原子操作**

    node tools/apply-decisions.cjs            只显示将要改什么，不写文件
    node tools/apply-decisions.cjs --apply    写数据、重跑 24 个校验、更新回归基线

## 1 它做四件事，按顺序

| 步骤 | 内容 |
| --- | --- |
| ① 列出改动 | 逐项对比现状与目标，输出「字段: 原值 → 新值」 |
| ② 写数据 | `economy-candidate.json` 的价格、工时、需求上限、混合路线排期；`demo-schedule.json` 的第 5 月说明 |
| ③ **重跑全部 24 个校验** | **任何一个失败就停下，且不更新基线** |
| ④ 更新回归基线 | 只有全部通过才执行 |

**第 ③ 步的关键是「失败就不更新基线」**——否则基线会把一个有问题的状态记成新的正确值

## 2 实测：它拦住了两个真问题

第一次 `--apply` 的结果是 **22 / 24 通过**，脚本拒绝更新基线并报出：

    FAILED: investments, difficulty

### 问题一：`check:difficulty` 的破产计数不公平

报错是 `normal goes bankrupt 1 times against hard's 0`。查下去发现这是**校验自身的缺陷**：困难档开局锁定量产与混合，所以它**可破产的组合本来就少**，按全部组合计数会让困难档显得最安全

**已修**：只比较**三档都开放的路线**（实际就是精品），同时把「全部路线」的数字也写进输出，不把真实情况藏起来：

    bankruptcyCounts:          { easy: 0, normal: 0, hard: 0 }      ← 同类比较
    bankruptcyCountsAllRoutes: { easy: 1, normal: 1, hard: 0 }      ← 如实记录

### 问题二（真实的设计问题）：固定排产在需求下降时会压垮简单档

全部路线口径下，**简单档与普通档各有一处破产**：`scale/demand_down_35`

逐月看清楚了原因：

| 月 | 计划(办/游) | 建造 | 售出 |
| ---: | --- | --- | --- |
| 1 | 6/1 | 6/1 | 3/1 |
| 4 | 14/5 | 14/5 | 7/3 |
| 6 | 22/10 | 22/10 | **11/5** |

**计划在需求下降 35% 时仍然满速爬坡，第 6 月造 32 台只卖出 16 台**——一半的产能变成库存，现金被压死

这**不是决策带来的**：普通档在决策落地前就会在这个场景破产；决策落地后简单档也进了同一条路

**这条发现把决策 5 的原始问题重新摆上桌。** 我在第 43 轮把决策 5 改写成「要不要让员工成为真实决策」，但真正的问题是更基本的那个：**固定排产不会对市场变化做出反应，所以需求下降会直接变成现金危机**——连「特别特别宽容」的简单档也不例外

## 3 顺带做的两处改动

**已记录的实测事实**：`check:investments` 原来把「招人不划算」硬编码在校验里。决策落地后困难档招人会变成 **+2763**（正是第 45 轮测出的那个涌现结果），硬编码的断言会误报

**已改为读 `design/recorded-facts.json`**，由 `apply-decisions.cjs` 在落地时同步重写。这样「招人在当前配置下值多少」是一个**被记录的事实**，而不是写死的期望——任何变动都会让校验报出差异并要求更新记录，而不是悄悄翻转一个设计决定

**导出清单**：新数据文件 `recorded-facts.json` 已按 `tooling` 分类，`check:export-coverage` 要求「设计目录下每个文件都必须分类」的规则因此继续成立
