# 覆盖校验的盲区

`check:coverage` 的职责是「**每个设计数据文件都必须有校验读取它**」

## 1 它只数了顶层

原来的枚举是：

    fs.readdirSync(path.join(root, 'design')).filter(f => f.endsWith('.json'))

**只读设计目录的顶层。** 而 `design/catalog-2016-2020/` 下有四个图鉴研究文件：

| 文件 |
| --- |
| `cpu-motherboard.json` |
| `gpu.json` |
| `memory-storage.json` |
| `structural.json` |

**实测：校验报告「27 个设计文件」，而实际有 31 个** ✗

## 2 那四个文件其实是被读的

`check-suppliers` 用**计算路径**读它们：

    read('design/catalog-2016-2020/' + file)

而覆盖校验的识别逻辑遇到这种写法时只记一个占位符 `(catalog)`——**不是文件名**，于是永远匹配不上任何条目

所以实际情况是：**覆盖是真的，但校验看不见** ✗ 一个「什么都没检查」的校验，和一个「检查了但看不出来」的校验，在报告上长得一模一样

## 3 已修

1. **枚举改成递归遍历整个 `design/` 树** → 31 个文件
2. **识别计算路径**：只要某个工具读的是图鉴目录，就记为它覆盖了那四个文件

修复后：**`designFiles: 31`**，校验通过 ✓

## 4 这一轮的实际收获

| 项目 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 校验声称覆盖的设计文件 | 27 | **31** |
| 未被任何校验读取的文件 | 0（但没数另外 4 个） | **0（31 个全数过）** |

**四个图鉴文件本来就有人读**，所以没有真的漏掉规则。但**如果将来有人只读顶层，校验不会发现**——现在会

## 5 一句话

「检查的东西对不对」和「检查的东西全不全」是两件事。这一轮修的是后者
