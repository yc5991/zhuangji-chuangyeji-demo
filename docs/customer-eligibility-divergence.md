# 客户资格判定：三处分歧，**游戏比模型更严**

第 96 轮对照客户资格判定：模型的 `satisfies()`（`check-customers.cjs`）与游戏的 `customerIssues()`（`game.ts` 第 224—236 行）

## 1 两边都有的检查

| 检查 | 模型 | 游戏 |
| --- | --- | --- |
| 兼容性（`blocked`） | ✓ | ✓（且游戏在打样与交付时也拦） |
| 最低内存 | ✓ | ✓ |
| 最低储存 | ✓ | ✓ |
| 独立显卡 | ✓ | ✓ |
| 最低显存 | ✓ | ✓ |
| 最高噪声 | ✓ | ✓ |
| 各项最低评分 | ✓ | ✓ |

**七项一致** ✓

## 2 游戏多出两处硬性要求

### 2.1 热稳定性（`coolingRatio >= 1`）

    if(t.coolingRatio<1) issues.push('压力测试不稳定');

**`customer-model.json` 里没有这个要求** ✗ 实测：`coolingRatio`、`thermalStable`、「压力测试」在该文件里**都不存在**

模型只在 `failureRateFor` 里把「热不稳定」当作**故障率倍率** ✓ 不作为资格否决 ✗

### 2.2 机身配色必须与客户偏好一致

    if(d.colors.body!==customer.color) issues.push(`客户偏好${...}机身`);

**`customer-model.json` 里没有颜色字段** ✗ 实测：`color`、`colour`、「机身」都不存在

而客户的颜色是**游戏随机生成的** ✗

    color: this.random()<.5 ? 'graphite' : 'silver'

**所以游戏要求玩家去猜一枚随机硬币** ✗ ——一个不在设计数据里、也不在模型里的硬性要求

## 3 第三处：预算比的是不同的东西

| | 比的基准 |
| --- | --- |
| **模型** | `a.budgetCoins[1]`——客群预算**区间的上限** |
| **游戏** | `customer.budget`——**每位客户抽到的**预算 |

`budgetCoins` 是区间（如 `[1950, 2350]`）✓ 游戏为每位客户抽一个值 ✓

**所以同一定价，模型放行，游戏可能拒绝**（当抽到的预算低于上限时）✗

## 4 三处分歧的共同方向：**模型高估需求**

| 分歧 | 效果 |
| --- | --- |
| 热稳定性要求 | 模型认为合格的设计，游戏可能拒 |
| 颜色要求 | 模型完全不知道有这个要求 |
| 预算按区间上限 | 模型比游戏宽松 |

**所以平衡模型算出的需求，比玩家实际能拿到的多。** 那 27 个设计校验验证的路线利润建立在偏乐观的需求上 ✗

## 5 配色这一条需要你决定

规格第 144 行：「风格设计 | 选择机身配色、部件外观和灯效，**回应客户偏好或品牌风格**」

**规格确认了颜色是玩法的一部分** ✓ **但没说必须是硬性匹配** ✗

| 选项 | 内容 |
| --- | --- |
| **L1** | **把颜色做成设计数据**：在 `customer-model.json` 里加颜色偏好（可为加权偏好而非硬性要求），模型与游戏都读它 |
| **L2** | **颜色不作硬性要求**：改为影响外观评分或接受度，而不是一票否决 |
| L3 | 保持现状：随机颜色 = 硬性要求，但**要把这条写进设计数据**，让模型也算上 |

**建议 L1 或 L2。** 理由：L3 会把「猜随机硬币」变成必经玩法；而规格说的是「回应偏好」，不是「必须一致」

## 6 热稳定性这一条同理

模型把热不稳定当作**故障率惩罚**（有代价但可接受）✓ 游戏当作**资格否决**（不可接受）✗

| 选项 | 内容 |
| --- | --- |
| **M1** | 模型也加上「热不稳定则客户拒收」，与游戏一致 |
| **M2** | 游戏改为只扣分不否决，与模型一致 |

**建议 M1 或 M2 择一，两边取齐。** 当前状态是「两边都有代价，但强度不同」，会让平衡与体感对不上

## 7 已加入实现校验的跟踪

这两条属于「设计数据里没有、游戏里有」的情况 ✗ ——第 94 轮那条校验查的是反方向（设计有、游戏没有）✗ **所以它抓不到这一种**

**它是第四类分歧**：**游戏有、设计数据没有**
