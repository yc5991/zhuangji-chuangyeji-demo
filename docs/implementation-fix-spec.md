## H1：口碑倍率封顶

| 项 | 内容 |
| --- | --- |
| **位置** | `game.ts` 第 410 行（`demandAssessment` 的返回） |
| **现状** | `expectedUnits: ... * fit * acceptance * this.state.reputation` |
| **改为** | `expectedUnits: ... * fit * acceptance * Math.min(1, this.state.reputation)` |

## M：热稳定性改为扣分而非否决

| 项 | 内容 |
| --- | --- |
| **位置** | `game.ts` 第 236 行（`customerIssues`） |
| **现状** | `if(t.coolingRatio<1) issues.push('压力测试不稳定')` |
| **原文锚点** | `coolingRatio<1) issues.push('压力测试不稳定')` |
| **两个方向** | **M1**：改为警告而非否决（`warnings` 而非 `issues`）——与模型一致<br>**M2**：保留否决，模型也加上同样规则 |
| **建议** | **M1**。模型把热不稳定当作故障率倍率（有代价、可接受），游戏当作一票否决（不可接受）。**取模型的做法**，因为「散热不足会更容易坏」比「散热不足就不卖」更有玩法 |

**若选 M1**，需同步：`check:customers` 的相关断言（若有）与 `docs/customer-gates.md`

## L：颜色要求

| 项 | 内容 |
| --- | --- |
| **位置** | `game.ts` 第 243 行（`customerIssues`） |
| **现状** | `if(d.colors.body!==customer.color) issues.push(...)` |
| **原文锚点** | `colors.body!==customer.color` |
| **问题** | 客户颜色是 `this.random()<.5?'graphite':'silver'` 生成的，**而 `customer-model.json` 完全没有颜色字段** |
| **三个方向** | **L1**：在 `customer-model.json` 加 `appearanceColorPreference`，模型与游戏都读<br>**L2**：颜色只影响外观评分，不否决<br>**L3**：保持否决，但把颜色写进设计数据让模型也算 |
| **建议** | **L2**。规格第 144 行说「回应客户偏好或品牌风格」——**回应**不等于**必须一致**。做成评分影响既保留玩法，又不逼玩家猜硬币 |

**若选 L2**，改动含：删掉该否决、在 `evaluateDimensions` 的 `appearance` 里加颜色匹配加成、`customer-model.json` 加颜色偏好字段

## 预算基准：模型改为逐客户抽取

| 项 | 内容 |
| --- | --- |
| **位置** | `tools/simulate-economy.cjs`（模型侧） |
| **现状** | 模型用 `budgetCoins[1]`（区间上限）；游戏用每位客户抽到的 `budget` |
| **建议** | **模型改为逐客户抽取**，与游戏一致 |
| **理由** | 游戏的做法更真实（每位客户预算不同），且模型改成抽取后需求估计更准 |

**代价**：模型需要引入随机性 ✗ 与「可复现」冲突 ✗ 折中：**用期望值代替抽样**——即按区间中位数计算接受度，而非上限 ✓

**建议采用折中方案**：模型用区间中点而非上限。这样既反映了「不是每位客户都能承受上限价」，又保持确定性 ✓
