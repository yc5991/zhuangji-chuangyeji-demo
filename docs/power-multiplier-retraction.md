# 撤回第 122 轮的发现：**供电倍率是可达的**

第 122 轮我说「`powerHeadroomBelowThreshold` 是死数据，252 种组合里 0 种触发」✗ **这是错的** ✓

## 1 为什么错了

我那一轮的枚举方式是：

    g.createDesign('office')   ← 固定用办公样机起步
    g.customize(d.id, { cpu, cooler, case, psu, gpu, fanCount: 2 })

**问题出在 `createDesign('office')`** ✗ 它的默认机箱是**小型机箱** ✓ 装不下 GTX 1080 ✓

**于是所有带独显的组合都被判为 blocked 而跳过** ✗ 我的枚举实际只覆盖了「办公机 + 换 CPU/散热/机箱」✓ 那些组合供电都很宽裕 ✓ 所以最低余量只有 0.310 ✓

## 2 正确的枚举结果

改用模型的 `evaluate`（它不预设立场）枚举 **126 种合法组合**：

| 项 | 数量 |
| --- | ---: |
| 合法组合 | 126 |
| **热不稳定** | **72** |
| **供电余量 < 0.2** | **36** |
| 最低供电余量 | **0.020** |

**两个条件都可达** ✓ 所以可靠性模型里的三个条件倍率**都会触发** ✓

## 3 游戏里也确认了

用游戏的 `evaluate` 直接测 `GTX 1080 + PSU 350`：

| 项 | 值 |
| --- | --- |
| 显卡需要 | 8-pin |
| PSU 350 提供 | 支持 6 与 8-pin ✓ **所以接线是合法的** |
| 额定 350W，显卡设计负载 175W | —— |
| **游戏算出的供电余量** | **0.15** ✓ **低于 0.2** |

**所以游戏里这个倍率也会触发** ✓

## 4 顺带看出的实质内容

`psu_350`（350W）配 `gpu_1080`（175W 负载）**在数据上是合法的** ✗ 它支持 8-pin ✓ 而余量只剩 15% ✓

**这在现实里很勉强，但在游戏里是一个「省电源钱」的真实选择** ✓ 而现在它**确实有代价**（故障率 ×1.8）✓ **这正是设计想要的** ✓

## 6 已撤回的与保留的

| 项 | 处理 |
| --- | --- |
| 第 122 轮的结论 | **撤回** ✓ 供电阈值不需要改（0.2 已经能触发） |
| 第 122 轮建议的「抬高阈值到 0.35」 | **撤回** ✓ 不需要 |
| **`check:reliability` 里新增的可达性检查** | **保留** ✓ 它枚举 126 种合法组合，要求两个条件都能触发 ✓ 而且它**正确地通过了** ✓ |

## 7 这条新校验的价值

它现在守着「设计里写了但永远不会发生」这类数 ✓ 思路是：

1. 从部件池枚举合法组合 ✓
2. 用模型的 `evaluate` 逐个判定 ✓
3. 要求 `reliability-model.json` 里每个条件倍率**至少有一种组合能触发** ✓

**它本轮没有报错——因为条件确实可达** ✓ 但**它抓到了我上一轮的错误** ✗ 因为我用它重做枚举时得到了完全不同的数字 ✓
