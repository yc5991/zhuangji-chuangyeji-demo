# 决定 5 和决定 E 是同一个情况：**游戏早就做到了**

决定 5 是「玩家可以在月结前修改下个月的产量」✗ 我原来把它当成一个要新增的机制 ✓ 本轮查了游戏代码，**它已经存在**。

## 1 游戏里的证据

| 位置 | 内容 |
| --- | --- |
| `game.ts` 第 304 行 | `schedule(designId, quantity=1, kind, customerId)`——**产量是参数** |
| `Orangegame.ts` 第 332 行 | 界面按钮：**「批量生产 N 台」** |
| `Orangegame.ts` 第 326 行 | 打样按钮 `g.schedule(d.id, 1, 'prototype')` |
| `Orangegame.ts` 第 140 行 | 「当前排产」面板 |

**所以玩家每个月都能自己决定排多少台** ✓ 不需要新增任何东西 ✓

## 2 那么「固定排产」是什么

「固定排产」是**平衡模型里的假设** ✗ 不是游戏规则 ✓

`simulate-economy.cjs` 用 `route.monthlyProductionTargets` 这张固定表 ✓ 因为模型要可复现 ✗ 所以它假定玩家按一张计划走 ✓

**玩家实际不这么玩** ✗ 他会随需求调整 ✓

## 3 这与决定 E 完全同型

| 项 | 我是怎么弄错的 | 实际 |

| **决定 5 改产量** | 读了模型，发现它是固定计划，就断定玩家改不了 | **游戏早就支持**（「批量生产 N 台」按钮） |

**同一个错误犯了两次**：把「模型做不到」当成「游戏做不到」✗

## 4 那这两项要做什么

| 项 | 要不要改游戏 | 要做什么 |
| --- | --- | --- |
| **决定 E** | **不要** | 让模型能提前采购，以便测出游戏本来就允许的玩法 |
| **决定 5** | **不要** | 让模型能按月调产量（第 79 轮已经这样测过） |

**两项都从「补一个缺失的玩法」变成「让模型追上游戏」** ✓

## 5 决定 5 的实测依据仍然成立

第 79 轮用模型的覆盖参数做过对照（需求下降 35%、量产路线）：

| 玩法 | 利润 | 结果 |

**这个测量是对的** ✓ 它测的是「如果玩家调产量会怎样」✗ 而游戏允许玩家调 ✓ 所以结论适用 ✓
