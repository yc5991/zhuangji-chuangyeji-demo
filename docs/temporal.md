# 时序一致性

设计数据里有多种时间表达方式，分散在不同文件里：

| 表达 | 所在文件 |
| --- | --- |
| **相对月份**（1—6） | 市场事件的预兆/结果月、逐月安排 |
| **绝对日期**（YYYY-MM-DD） | 工作台的新品日期 |
| **月份**（YYYY-MM） | 2016—2020 目录的 72 个事件 |
| **年份** | 年代趋势、公司成长阶梯 |

分项校验各自检查自己那一块，**但没有任何一个检查「这些时间说的是不是同一件事」**

`npm run check:temporal` 补上这一层

## 1 检查的四条时序

**① Demo 窗口**：固定为 2016-01 至 2016-06。市场事件的预兆月、结果月、持续月全部映射到绝对日期后必须落在窗口内

**② 新品日期**：工作台登记的四个新品日期必须落在 Demo 窗口内，**且必须写明日期依据**——`2016-05-06` 标为 `game_forecast_date`，`2016-05-27` 等标为 `graphics_platform_release`，不能是不明来源的数字

**③ 完整版时间线**：年代趋势必须从 Demo 那一年（2016）开始、连续覆盖到 2030；成长阶梯的第一阶段必须就是 Demo 开局那一年，各阶段年份都落在 2016—2030 内

**④ 配件可用性**：每个样机用的配件都必须在**第一个月就能买到**。若有配件晚于 Demo 开始才上市，样机在开局就做不出来

## 2 实测结果

| 项目 | 结果 |
| --- | --- |
| Demo 窗口 | 2016-01 至 2016-06 |
| 工作台新品日期 | 4 个，全部在窗口内且有依据 |
| 目录窗口 | 2016-01 至 2020-12，72 个事件 |
| 四套样机 | 最晚配件均为 2016-01-01，**开局即可制作** |
| 完整版时间线 | 2016—2030 连续 |

## 3 已实测能抓到问题

把工作台最后一个新品日期改成 `2016-08-15`，校验立刻报出：

    workbench event 2016-08-15 falls after the Demo ends

恢复后立即回到通过

## 4 记录的缺口

目录覆盖到 **2020-12**，而年代趋势与成长阶梯延伸到 **2030**——**中间 10 年没有配件数据**。校验把这个缺口写进输出而不是忽略：它是已知的外部资料缺口，不是可以靠调数值补上的
