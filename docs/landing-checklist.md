## 3 两类需要特别注意的改动

### 3.1 扩产利润的两个数字要「作废」而不是「更新」

61956（计划 ×1.5 的利润）与 64733（扩产上限利润）在方案下**不再成立**——精品被老板工时封顶，扩产这条路被堵死了

这两处不能简单替换成新数字，必须**改写结论**：原文说「精品扩产可以做到 ×1.5，利润 61956，约为量产的 2 倍」，方案后应改为「精品受老板 96 小时设计工时封顶，任何投资都无法扩产」

### 3.2 路线平衡三方矛盾的整节需要重写

[Demo 详细设计候选](design-candidates.md) 的 4.2 节记录的是「四条规则无法同时成立」的证明过程。方案落地后这个矛盾已经解开，该节应从「未解决问题」改为「已解决记录」，保留证明过程作为设计依据

## 4 落地时的完整顺序

1. 写入数值：`design/economy-candidate.json`（工时、售价、混合计划与投资）、`design/customer-model.json`（若选放大客群）
2. 按本清单更新 39 处文档数字，并改写 3.1、3.2 两节
3. 重新生成回归基线：`npm run baseline:update`
4. 重跑十三个校验与 `preview:proposal`，确认全部通过
5. 更新 [目标达成度审计](../design/completion-audit.json)：五项从 `pending_decision` 改为 `complete`，`check:audit` 应报告 `complete`

## 5 为什么先做这份清单

前几轮出现过文档数字过期（第 13 轮发现难度月数表还写着 6.0 / 1.9 / 1.3，实际已是 8.0 / 2.1 / 1.2）。落地会一次改动十几个数值，散在三个文件里，靠人工找一定会漏

先把清单生成出来，落地就变成一次机械替换加两处改写，不会留下自相矛盾的文档
