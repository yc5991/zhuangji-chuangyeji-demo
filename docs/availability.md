# 上市时间与产能

`workbench.json` 的 `scheduleRules` 里有一条 Demo 规则：

    lateReleaseCannotUseFullMonthCapacity: true

**中途上市的配件不能占用整个月的产能。** 但这轮检查发现，仿真器不但没实现这条，还漏掉了更基本的一条：

## 查出的两个问题

**① 配件还没上市就能用来造机器**

仿真器只读 `components.json` 的 `game.basePriceCoins` 等数值，**完全不看 `availability.gameDate`**。所以玩家在 2016 年 1 月就可以用 5 月 27 日才上市的显卡造机器

**② 上市当月的产能没有折算**

上面那条规则要求中途上市只能占用当月剩余的时间，仿真器也没做

## 实测证据

把游戏配方的显卡换成 **2016-05-27** 上市的 `gpu_1080`，修复前的逐月产量：

| 月 | 修复前 | 修复后 |
| ---: | ---: | ---: |
| 1 | 1 | **0** |
| 2 | 2 | **0** |
| 3 | 3 | **0** |
| 4 | 5 | **0** |
| 5 | 8 → **2** | **2** |
| 6 | 10 | 10 |

修复前 1—4 月都在用一块还没上市的显卡造机器；修复后上市前为 0，上市当月按当月剩余 5/31 天折算为 0.161，次月恢复满产

## 实现

新增 `releaseCapacityFactor(productId, month)`：

| 情况 | 系数 |
| --- | ---: |
| 配件在更早的月份上市 | 1 |
| 配件在该月上市 | 当月剩余天数 ÷ 当月天数 |
| 配件尚未上市 | **0** |
| 配件晚于 Demo 窗口 | **0**（六个月里都拿不到） |

## 对现有数值的影响

**零。** 四套配方最晚的配件都是 2016-01-01，全部开局即有，所以回归基线保持 `unchanged`

但这条规则**对玩家实际游玩有影响**：目录里有四个配件是在 Demo 中途上市的，玩家一旦选它们就会遇到这条限制

## 已实测能抓到问题

`check:seams` 新增一条规则，直接验证这个函数：

- 用最晚上市的配件构造一个假配方
- **上市之前的每一个月，系数必须是 0**
- **上市当月必须严格介于 0 与 1 之间**（既不能满产，也不能完全造不出）
- **次月必须是 1**
- 全部配件开局即有的配方不受影响
- 同时确认仿真器**真的把这个系数用在产量上**（而不是算出来没人用）

实测结果：`gpu_1080`，上市月 5，当月系数 **0.161**

## 与 already 定义的供应参数的关系

`supplier-system.json` 还定义了 `nominalDeliverySimHours`（现货 2 小时、经销 8 小时、预约批次 24 小时）等交付参数。这些是**完整版采购流程的草案**，Demo 仿真器不模拟采购在途（仿真器的 limitations 里已写明）

本轮实现的是**配件能否买到**（availability），不是**采购要等多久**（lead time）。两者是不同的问题，前者是 Demo 内就成立的硬约束
