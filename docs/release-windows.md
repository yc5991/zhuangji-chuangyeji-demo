# 上市窗口与游戏日期的一致性

配件有两个关于「什么时候出现」的字段，来源完全不同：

| 字段 | 来源 | 性质 |
| --- | --- | --- |
| `reference.specs.releaseWindow` | 厂商证据 | **已核实** |
| `availability.gameDate` | 游戏设计 | **假设** |

假设**不能与证据矛盾**：如果游戏在某个配件真实上市之前就把它摆上货架，那就是凭空造出了一个不存在的产品。这条此前没有任何校验

## 1 补上的规则

`check:temporal` 新增：**游戏日期不得早于该配件自己证据里记录的上市窗口**

窗口支持三种写法：

| 写法 | 例 | 解析为 |
| --- | --- | --- |
| 年 + 季度 | `2015-Q3` | 2015 年 7 月 |
| 年 + 月 | `2016-05` | 2016 年 5 月 |
| 只有年 | `2012` | 2012 年 1 月（最粗的写法，取当年起点） |

**只有年的写法是校验跑出来才发现的**：第一次运行时报出 `cpu_fx8350: release window 2012 is not a month or a quarter`，才知道数据里有第三种格式

## 2 覆盖率如实记录

**32 个配件里只有 4 个带有上市窗口**——只有这 4 个的参考规格里记录了窗口，其余 28 个没有，无法与证据对照

校验把覆盖率写进输出，而不是让「通过」暗示全部检查过了：

    releaseWindowCoverage: { checked: 4, parts: 32, note: '其余配件的参考规格里没有上市窗口' }

带窗口的 4 个都是处理器：

| 配件 | 参考窗口 | 游戏日期 |
| --- | --- | --- |
| cpu_6100 | 2015-Q3 | 2016-01-01 |
| cpu_6500 | 2015-Q3 | 2016-01-01 |
| cpu_6700 | 2015-Q3 | 2016-01-01 |
| cpu_fx8350 | 2012 | 2016-01-01 |

其余 28 个配件的 `dateBasis` 是 `demo_opening_assumption`（Demo 假设开局即有），另外 4 个是 `graphics_platform_release`（有真实上市日期），见 [时序一致性](temporal.md)

## 3 已实测能抓到问题

把 `cpu_6700` 的游戏日期改成 `2015-01-01`（证据说 2015-Q3）：

    cpu_6700: the game offers it from 2015-01-01, before the 2015-Q3 release window the evidence records

恢复后立即回到通过

## 4 与上一轮的关系

上一轮补的是**配件能否买到**（availability 决定产能），这一轮补的是**游戏日期有没有与证据矛盾**。两者合起来，配件的时间维度在 Demo 内是完整的：

| 问题 | 由谁保证 |
| --- | --- |
| 这个配件在游戏里什么时候能买 | `availability.gameDate` + 上一轮的产能规则 |
| 这个日期有没有早于真实上市 | 本轮的上市窗口校验 |
| 这个日期有没有晚于 Demo 窗口 | `check:temporal` 的窗口检查 |
