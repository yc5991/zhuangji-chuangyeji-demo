## 4 真正的问题：**评价规则是硬编码的，不是读数据**

`workbench.ts` 的 `evaluate()`（第 189—237 行）把整套评价写死在 TypeScript 里：

- 兼容性检查（插槽、代际、尺寸、供电）逐条硬编码
- 评分公式（办公/游戏/创作）硬编码权重
- 噪声、温度、负载的计算硬编码

**而 `design/evaluation.json` 定义了六个维度，`check:evaluation` 在守它，`check:seams` 验证它的数值被读取**——**但读它的是仿真器，不是游戏** ✗

**后果：改 `evaluation.json` 不会改变游戏。** 改设计数据只影响平衡模型，游戏照旧

## 5 没有校验在检查这件事

| 校验 | 查什么 | 查得到游戏吗 |
| --- | --- | --- |
| `check:wiring` | 设计文件里的数值被**机制**读取 | 查的是 `simulate-economy.cjs`，**不是游戏** ✗ |
| `check:seams` | 设计里的维度被消费 | 同上 ✗ |
| `check:coverage` | 设计文件有校验读取 | 同上 ✗ |

**所以「设计文件里的规则是否被游戏实现」完全没有校验** ✗ ——这正是第 90、92 两轮能连续找到分歧的原因

## 6 建议

| # | 内容 |

| **J** | **建立「设计 → 游戏」的实现校验**：至少检查 `data.ts` 携带的键与游戏引用的键一致、以及被硬编码的核心规则（评价维度、兼容性检查）与设计数据同源 |

**这不能靠现有校验补**——它们都指向仿真器。需要一条新的检查，或让游戏改为读数据
