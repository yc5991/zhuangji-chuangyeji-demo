# 逐月安排里记着一个缺口，而它的「阻塞原因」已经过时

`design/demo-schedule.json` 有一个 `openGaps` 字段 ✓ **设计文件自己记录未解决的问题**——这是一个好做法

## 1 原记录

> **subject**：精品与混合路线在第 5—6 月没有投资机会
> **blockedBy**：docs/design-candidates.md 4.2 的**路线规则三选二，未定之前无法给精品安排一个能回本的第 5 月投资**

## 2 为什么过时

「路线规则三选二」在第 21 轮就已定论 ✓（取产能约束，即决策 1）✗ 所以「未定之前」这个前提不再成立 ✗

而真正的结论是第 91 轮测出来的：

> **精品路线没有可买的设备**——台位增加的是台位工时，而精品受老板 96 小时限制，**加台位反而亏损 1440 币**

**所以缺口不是「规则没定」，而是「精品物理上买不到有效投资」** ✗ 两者是不同的结论 ✓

## 3 已更新

| 字段 | 更新后 |
| --- | --- |
| `subject` | 保持原样（两条路线都还没有第 5 月投资，这是当前数据的实况） |
| `detail` | 补上实测：精品加台位 −1440 币 |
| `blockedBy` | 改为「待用户在决策包中确认决策 6」 |
| `evidence` | **新增字段**，指向 `docs/decisions.md` 与两份实测文档 |

## 4 顺带确认了一件事：校验在守这个字段

我改窄了 `subject` 后，`check:schedule` 立刻报错：

    boutique, mixed have no month 5-6 investment, which must be recorded as an open gap

**它要求两条缺失第 5 月投资的路线都被记进 `openGaps`** ✓ 所以这个字段不是装饰，是受校验保护的 ✓

**我的改动被拦下了，恢复 subject 后通过** ✓ ——这是校验起作用的又一个例子

## 5 这件事的意义

**设计文件里的「未解决问题」列表会随时间过时。** `openGaps` 是好机制，但它的内容需要跟着结论更新 ✓

第 59 轮发现完成度审计过时 ✗ 第 70—71 轮发现交接说明与四份文档过时 ✗ **这次是设计数据内部的缺口记录** ✗

**共同点**：记录「问题状态」的地方最容易过时，因为它不参与计算，没有校验会因为它错而失败 ✗

（`openGaps` 的结构受校验保护 ✓ 但它的**文字内容**不受保护 ✗ ——因为没有任何程序会去读那段散文）
