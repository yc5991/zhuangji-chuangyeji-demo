# 重大更正：决策 E 的前提是错的——**游戏已经实现了提前备货**

第 80—81 轮我记录了这样一条：

> **困难档精品碰上「内存明显上涨」必死**，而 `market-events.json` 承诺的「提前备货」在仿真器里做不到
>
> 建议 E1：**实现预兆期提前备货机制**

**第 101 轮发现这条记录是错的。**

## 1 游戏里早就有提前备货

`tests/content.test.cjs` 的第一个用例就在测这件事 ✓ 我此前从没读过这个文件（第 101 轮才发现有第二个测试文件）

用例名：**`market omen, saved outcome and expiry change only new purchases`**

关键断言：

| 行 | 断言 | 含义 |
| --- | --- | --- |
| 21 | 在第 3 月（预兆月）买入内存 | 玩家可以在预兆期下单 |
| **26** | **`incoming.unitCost === base`** | **预兆期下的单，第 4 月到货时仍按预兆价** ✓ |
| 29 | 到货后库存批次的成本仍是 `base` | 批次保留采购价 ✓ |
| 25 | 第 4 月**新**采购的单价高于 `base` | 涨价只影响新单 ✓ |
| 30 | 涨价后再下单，成本等于现价 | ✓ |
| 32 | 事件结束后价格回到 `base` | ✓ |

**机制实现得很完整** ✓ 而且 `market.ts` 第 44 行的 `categoryPriceFactor` 写得清楚：倍率只在 `state.month >= r.resolveMonth` 时生效 ✓ ——**预兆月价格不变，所以那时候买就是备货** ✓

## 2 所以三件事要分开

| 说法 | 对错 |
| --- | --- |
| 「设计承诺的提前备货没实现」 | **错——游戏实现了** ✗ |
| 「平衡模型不会提前备货」 | **对** ✓ 模型按月以当时价格采购 |
| 「困难档精品必死」 | **错——那是模型的结论，不是游戏的** ✗ |

**模型算出的「困难档精品第 5 月破产」，在真实游戏里玩家可以靠备货避免。**

## 3 决策 E 因此要改写

| | 原表述 | 更正后 |
| --- | --- | --- |
| **是什么** | 游戏缺一个机制 | **模型缺一个测量能力** |
| **要做什么** | 在游戏里实现提前备货 | **让模型也能提前采购，以测出游戏本来就允许的玩法** |
| **影响** | 游戏会变简单 | **平衡数值会变准** |

**它不再是「补一个缺失的玩法」，而是「让模型追上游戏」。**

## 4 为什么这个错误值得记下来

我在第 80—81 轮做了三件事：

1. 扫出 54 组里的 3 个破产 ✓ 这是对的
2. 确认只有一个对应真实事件 ✓ 这也是对的
3. **推断「唯一活路没实现」** ✗ **这一步错了**

**错在把「模型做不到」当成了「游戏做不到」。** 我检查了 `simulate-economy.cjs`，发现它不会提前采购，就下了结论 ✗ ——**而游戏是另一个程序，它有这个能力**

**这是第 61—98 轮反复出现的同一类错误的又一次**：用一个局部的读数推出全局结论 ✗ 前几次分别在出处规则、办公定价、截断行上，这次是在「谁实现了什么」上

## 6 教训

**「模型怎么做」和「游戏怎么做」是两个问题。** 我在第 89 轮才发现游戏实现可以被检查，而在此之前我以为模型的结论就是游戏的事实 ✗

**以后再遇到「设计承诺了 X，但没实现」的说法，要先问是哪个程序没实现。**
