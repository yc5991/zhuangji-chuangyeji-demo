# 评价六维：模型有，游戏显示的是**另一套数**

规格第 119 行确认：「产品评价覆盖**用途、性能、温度、噪声、外观和成本**」

`design/evaluation.json` 定义了这六个维度的算法，`check:evaluation` 与 `check:seams` 守着它 ✓ **但它们查的是仿真器，不是游戏**

## 1 逐维对照

| 规格维度 | 模型（`evaluateDimensions`） | 游戏显示 | 一致？ |
| --- | --- | --- | --- |
| **用途** | `scores[target]` | `办公 x 游戏 y 创作 z` | ⚠️ 游戏显示三个分，不是一个 |
| **性能** | `100 × (三分之和 / 260)` | **没有** | **❌ 缺失** |
| **温度** | 热稳定得 60 分起 + 供电余量，不稳定则扣 | `稳定度 {coolingRatio}%`（0—100 的比率） | **❌ 不同的量** |
| **噪声** | `100 × (1 − 负担/120)`（0—100 分） | `噪声 {noiseBurden}`（原始负担值） | **❌ 不同刻度** |
| **外观** | 工艺档的外观分 | `外观 {appearance}` | ⚠️ 游戏内联计算，未读工艺档 |
| **成本** | 配件成本占预算比例（0—100 分） | 配置页的 `¥{partsCost}` 原始金额 | **❌ 不同刻度** |

**六个维度里，一个完全没有，四个用的是不同的量或刻度。**

**游戏另外显示了两个设计里没有的量**：`稳定度`（冷却比率）与 `理线`（整洁度）

## 2 后果

### 2.1 玩家看到的是不同的数

同一个属性，模型说「噪声 62 分」，游戏说「噪声 45」✗ **两个数都对，但说的不是同一件事**

**若客户偏好或界面说明按模型的分制写，玩家会对不上。**

### 2.2 「性能」这个维度在游戏里不存在

模型的 `performance` 衡量「绝对能力」（三个用途分之和 / 260），用途单一但极强的机器与三项均衡的机器在这里得分不同 ✓

**游戏没有这个数，所以玩家无法看到「这台机器整体有多强」** ✗

### 2.3 客户决策用的是原始值，不是维度分

游戏的 `demandAssessment` 用 `test.scores[...]`、`test.noise`、`test.ramGB` 等原始值判断资格 ✗ 而模型用维度分 ✓

**两边判断的结论可能一致**（都在比同一批原始量），**但呈现给玩家的分层不同** ✗

## 3 这属于哪一类问题

| 轮 | 发现 | 类型 |
| --- | --- | --- |
| 90 | 口碑倍率不封顶 | 实现与设计**不一致** |
| 92 | 可靠性未实现 | 设计有、**游戏完全没有** |
| **95** | **评价六维刻度不同** | **两边都有，但说的不是同一套数** |

**第三类**：不是缺失，也不是矛盾，而是**两套并行的表达** ✗

## 4 建议

| # | 内容 |
| --- | --- |
| **K** | **让游戏显示设计定义的六个维度分**：把 `evaluation.json` 传进 `data.ts`，在游戏里实现 `evaluateDimensions` 的六个公式，界面改为显示六个 0—100 的分（原始值可作为补充信息） |

**理由**：

1. 规格第 119 行确认了这六个维度，**它们是玩家可见的内容**
2. `evaluation.json` 的 `rules` 写明「每个维度要么被客户决策读取，要么显式标为 informational」——**这条规则在模型里成立，在游戏里不成立**（游戏根本没有这些维度）
3. 分制统一后，界面说明与数值可以对齐

## 5 已加入实现校验的跟踪清单

`check:design-to-game` 的 `GAME_MUST_IMPLEMENT` 现在包含 `evaluation.json`，**并且它报出了一个新缺口** ✓

**这正是第 94 轮建这条校验的目的**：它能抓「设计有、游戏完全没有」，而本轮的六维刻度差异属于第三类（两边都有但不同），**仍需人工对照** ✓
