# 实现缺口：**可靠性模型完全没有实现**

第 92 轮对照发现：`design/reliability-model.json` 有三个机制，**游戏一个都没实现**

## 1 逐项对照

| `reliability-model.json` 的机制 | 内容 | 模型 | 游戏 |
| --- | --- | --- | --- |
| **`failureRate`** | 基础故障率 + 温度/供电/测试的条件倍率 | ✅ | **❌ 未引用** |
| **`qualityControl`** | 测试时长决定故障逃逸率（不测 1.0 / 部分 0.3 / 完整 0.06） | ✅ | **❌ 未引用** |
| **`arrivalDefect`** | 到货缺陷：退款 + 物流 120 币 + 口碑 −0.15 | ✅ | **❌ 未引用** |
| `rework` | 返工工时与耗材 | ✅ | ⚠️ **见下** |

**实测**：在 `assets/scripts/` 全部 TypeScript 里搜索这三个键，**零引用**

## 2 游戏里的「rework」不是可靠性返工

`game.ts` 确实有 `rework` 这个词，但看它的用法：

    missing(designId, quantity = 1, rework = true) {
      const old = rework && quantity === 1 ? this.reusable(d) : undefined;

**它的意思是「改配一台已经做好的机器，复用可保留的配件」**——是玩家的**改设计**操作，不是**故障返工**

所以：**可靠性模型在游戏里完全没有实现**

## 3 后果

### 3.1 游戏里不会出现故障

模型里每台机器都有故障率（基础值 × 温度倍率 × 供电倍率 × 测试倍率），游戏里没有——**做出来的机器一定能用**

### 3.2 「测试多久」这个决策在游戏里没有意义

模型里：

| 测试时长 | 故障逃逸率 |
| --- | ---: |
| 不测试 | 1.00 |
| 部分测试（≥0.5 小时） | 0.30 |
| 完整测试（≥1 小时） | 0.06 |

**游戏里没有逃逸率，所以多测只是多花工时、没有任何好处** ✗ 这会把一个设计好的决策变成纯成本

### 3.3 模型预测的难度高于实际游戏

模型按期望值计入故障、返工与到货缺陷的成本 ✗ 游戏不计 ✗

**所以那 26 个设计校验验证的平衡，比玩家实际会遇到的更严苛**
